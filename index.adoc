== Abstract

This document is the official technical specification of the **{doc-name}** standardised
by the **{organization}** (CNA).
It defines, in a language-agnostic way (using a notation inspired by the Kotlin language), the interfaces,
classes, enumerations, errors, structural relationships and behavioural requirements that any conforming
implementation of the {doc-name} MUST satisfy.

The {doc-name} is the *application-facing* surface used by terminal applications to operate Calypso transit and ticketing cards.
It builds on top of the *Terminal Reader API* (<<ref_cna_tr,CNA-TR-API>>) and delegates every cryptographic operation to a symmetric (<<ref_cna_tccs,CNA-TCCS-API>>) or asymmetric (<<ref_cna_tcca,CNA-TCCA-API>>) crypto module.

== Introduction

=== Purpose

The {doc-name} defines the public surface used by terminal applications to:

* select a Calypso card through a <<ref_cna_tr,CNA-TR-API>> selection scenario enriched with Calypso-specific commands;
* operate read-only transactions without involving a crypto module (*free* transaction);
* operate fully authenticated transactions using a *symmetric* crypto module (<<ref_cna_tccs,CNA-TCCS-API>>) -- either in the
*regular* mode (compatible with every Calypso product) or in the *extended* mode (additional features only available on Calypso Prime Extended);
* operate fully authenticated transactions using an *asymmetric* crypto module (<<ref_cna_tcca,CNA-TCCA-API>>) in *PKI* mode;
* expose a dynamic view of the card (`CalypsoCard`) updated throughout the transaction.

=== Scope

This specification covers:

* the factory used to instantiate the public types of the API (`CalypsoCardApiFactory`);
* the data model of a Calypso card (`CalypsoCard`, `ElementaryFile`, `FileHeader`, `DirectoryHeader`, Stored Value log records);
* the selection extension (`CalypsoCardSelectionExtension`);
* the family of transaction managers (Free, Secure Regular, Secure Extended, Secure PKI);
* the *symmetric* and *asymmetric* security settings carriers;
* the *Stored Value* operations and *Search Record Multiple* support;
* the SPIs implemented by *crypto modules* to plug into the secure transaction managers;
* the family of errors raised during a Calypso transaction.

The following topics are *out of scope*:

* the on-the-wire APDU dialog with the card (handled internally by the implementation);
* the cryptographic algorithms themselves -- only the SPI contract is normative;
* the on-the-wire transport between the terminal and any remote ticketing system.

[[sec_conformance]]
=== Conformance

A software product conforms to this specification if and only if:

. it implements every interface and class defined in <<sec_specification>> with the operations and semantics
  prescribed in this document,
. it raises errors exclusively of the types defined in <<sec_errors>> for the situations described,
. it preserves the structural relationships described in <<sec_architecture>>.

Throughout this specification, the key words **MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT**, **RECOMMENDED**,
**MAY** and **OPTIONAL** are to be interpreted as described in <<ref_rfc2119,RFC 2119>> and <<ref_rfc8174,RFC 8174>> when, and only when,
they appear in all capitals.

In conformance with <<ref_rfc2119,RFC 2119>>, **SHALL** is equivalent to **MUST**; this specification uses **MUST** exclusively in
order to avoid ambiguity.

==== Operation contracts

To avoid repetition, the following rules apply to every operation table in <<sec_specification>> and are therefore
not restated for each operation:

* *Pre-conditions.* The *Pre-conditions* row states what the caller MUST guarantee before invoking the
  operation. Violating one is a contract error, never listed in the *Errors* row, which describes only the
  outcomes a correct caller must handle. Each entry is prefixed by its nature, which determines the error
  raised when the condition is not met:
** *Argument* -- an illegal argument error. Applies to any invalid argument, including values bounded by a card or SAM protocol.
** *Range* -- an index out of bounds error. Applies when the argument designates a position within a collection or memory image exposed by the API.
** *State* -- an illegal state error.
** *Capability* -- an unsupported operation error.
* *Non-`null` results.* Unless the return type is marked nullable (`T?`) or the *Returns* row states otherwise, an
  operation returns a non-`null` value.
* *Collections.* Unless the return type is marked nullable (`T?`), an operation whose return type is a collection
  (e.g. `List`, `Set`, `Map`) returns an empty collection rather than `null`.
* *Fluent composition.* Builder-style operations return the current instance so that calls can be chained.

==== Concurrency

Unless explicitly stated otherwise, the stateful types defined by this specification are *not* thread-safe. A given
instance MUST be accessed from a single thread at a time; concurrent use of the same instance without external
synchronisation results in undefined behaviour. Distinct instances MAY be used concurrently.

[[sec_maxduration]]
=== Command exchange duration bounds

As a countermeasure against relay attacks, the duration of the most sensitive command exchanges MAY be bounded: a
relay adds a transmission delay, so that an abnormally long exchange reveals that the card is not actually present
in front of the reader.

This specification exposes *no operation* for it. A usable bound is the sum of two budgets held by two different
parties: the computation time of the card, which depends on its product type and on the key used, and the latency
of the terminal, which depends on the coupler, the antenna, the driver and the execution platform. Neither is known
to the ticketing application, and the calibration that establishes them is performed against the very implementation
that will be deployed. The countermeasure is therefore *entirely handled by the implementation*, which obtains its
configuration by its own means, outside the surface of this API -- as a reader driver obtains its technical
parameters when it is instantiated.

The subsections that follow are addressed to the *implementer*: they state which exchanges carry the countermeasure,
through which mechanism it is applied and what MUST happen when a bound is exceeded. The last one states what the
ticketing application sees of it.

==== Bounded command exchanges

A bound applies to a *single* command exchange, measured from the transmission of the command to the reception of
its response; the other commands of the secure session or of the Stored Value operation are not included. The
exchanges that carry the countermeasure are:

* the *Open Secure Session* command;
* the *Close Secure Session* command;
* the *SV Reload*, *SV Debit* and *SV Undebit* commands, which exist in symmetric-key transactions only.

These are the exchanges a relay has an interest in carrying: the first two frame the authentication of the card,
the last ones commit a Stored Value movement. The other commands of a transaction are not bounded, and an
implementation SHOULD NOT bound them: their duration varies with the volume of data exchanged, so a bound would
yield false positives without adding protection.

==== Mechanism

The <<ref_cna_tc,CNA-TC-API>>, through which the implementation exchanges APDUs with the reader, provides what is
needed, in microseconds:

* a maximum tolerated duration declared on each request (`ApduRequest.apduExchangeMaxDurationUs`), which the reader
  layer enforces by raising `ApduExchangeDurationExceeded`;
* the effective duration measured on each response (`ApduResponse.apduExchangeDurationUs`), or `null` when the
  reader does not provide the measurement.

An implementation therefore has two ways of applying a bound, which are not equivalent:

. *Declared on the request.* The bound is resolved before the exchange and the reader enforces it. This is the
  direct way, and the only one available when the reader alone is able to measure.
. *Checked on the response.* The implementation reads the effective duration from the response and compares it
  itself. The bound is then resolved *after* the exchange, which is what allows it to depend on data that the
  exchange itself reveals -- typically the KIF and KVC returned by *Open Secure Session*, which identify the key,
  and therefore the computation time, of the card that has just answered.

Only the implementation holds what a bound must be resolved from: the product type of the card, the key used and
the characteristics of the reader in use. That resolution, and the configuration it reads, are outside the scope of
this specification.

An implementation MUST NOT let a transaction pass for a protected one when the countermeasure could not be applied.
When no measurement is available -- the reader neither enforces a declared bound nor reports an effective duration
-- the implementation reports that condition by its own means instead of remaining silent.

==== Behaviour on overrun

When the effective duration of a bounded command exchange exceeds the applicable bound, the exchange MUST be
reported as failed and the error propagated to the application as an `InvalidCardResponse`
(<<ref_cna_tr,CNA-TR-API>>).

* *A secure session is open.* The session MUST be cancelled automatically before the error is propagated, so that no
  modification performed during the session is validated by the card.
* *No secure session is open* (a Stored Value command executed outside a session). There is nothing to cancel: only
  the error is propagated, and the ticketing application decides what to do according to its own context (for example
  retrying the operation, rejecting the card or raising an alert).

==== What the ticketing application sees

The application configures nothing and is not told whether a bound applies: whether the countermeasure is active,
and how it is tuned, is a property of the implementation and of the terminal it runs on, not of this API. Two
consequences follow:

* `InvalidCardResponse` may arise from a duration overrun as well as from a malformed response. An application that
  already handles that error needs no change.
* Absent such a configuration, no bound applies and no protection exists. The presence of this section is not, in
  itself, an indication that a given terminal is protected.

[[sec_hce_validity]]
=== HCE token validity

The application serial number of a *Calypso HCE* application is made of two fields: the two most significant bytes,
the *SN Header*, carry the date and time of end of validity of the token, coded as the number of half-days
elapsed since 1 January 2010 at 0:00 **local time**; the six remaining bytes are the SN Value, which identifies the
application. The header is not significant when it is equal to `0`. An HCE application is recognised by the two
most significant bits of the fourth byte of its serial number.

What that validity materialises depends on the cryptographic nature of the transaction: in symmetric-key mode it is
the end of validity of the *debit key*; in PKI mode it is the expiry date of the key carried by the card
certificate. This API names the token, which has a single validity window whatever the mode.

The reference being local, the terminal and the issuer of the token MUST share the same local time reference. The
resolution of the encoding is half a day, so a difference of time zone between them shifts the boundary of the
validity window by the corresponding offset.

Nothing in the card dialogue reveals an outdated header. In symmetric-key mode, the header takes part in the
diversification of the keys, so a card whose validity window has passed still authenticates normally. In PKI mode,
the expiry is attested by the card certificate and is not signalled by the card either. The verification therefore
belongs to the terminal, and this specification splits it in three.

*Decoding.* <<op_CalypsoCard_getHceTokenExpiryLocalEpochSeconds,`CalypsoCard.getHceTokenExpiryLocalEpochSeconds`>> exposes the
decoded header, converted into the number of seconds elapsed since 1 January 1970 at 0:00 local time, so that the
ticketing layer can display it without knowing the Calypso encoding. It is part of the card image, and is therefore
carried by an exported processed selection scenario.
<<op_CalypsoCard_getApplicationSerialNumber,`getApplicationSerialNumber`>> keeps exposing the serial number with its
two most significant bytes forced to `0`, so that the identity of the application does not change when its token
is renewed.

*Verification.* The comparison belongs to this specification, which owns the Calypso encoding; what it lacks is a
clock. The application therefore provides a <<type_HceTimeProvider,`HceTimeProvider`>>, registered through
<<op_CalypsoCardApiFactory_setHceTimeProvider,`CalypsoCardApiFactory.setHceTimeProvider`>>, which returns
the current time expressed in the same reference as the SN Header, that is **local** time. The token is valid while that time precedes the end of validity carried by the SN
Header. The provider is consulted when the response to the selection is parsed, by the side that holds the card
extension. It is a local component: it is never part of an exported selection scenario.

*Reporting.* The outcome is always exposed, and never hides the card: an application whose token has expired is
selected like any other, and <<op_CalypsoCard_isHceTokenValid,`CalypsoCard.isHceTokenValid`>> reports the
verdict, so that the ticketing layer can decide what to do -- refuse the service, invite the holder to renew the
token, or log the event.

[cols="^.^3,^.^1", options="header"]
|===
| Situation | `isHceTokenValid()`

| The application is not HCE, or its SN Header is not significant | `null`
| The validity has been evaluated | `true` or `false`
| No time provider has been registered | `null`
|===

*Protection.* Because the card itself does not enforce the validity window, no secure session may be opened with an
HCE application whose token has expired or could not be verified. The verdict being known as soon as the card
is selected, this is stated as a *State* pre-condition of the session opening operations rather than as an error
raised during the exchange: an application that prepares such an opening violates the contract. This applies to
every secure session, whatever its mode and its write access level. An application that accepts the risk lifts the
constraint with
<<op_SecuritySettings_authorizeExpiredHceToken,`SecuritySettings.authorizeExpiredHceToken`>>.

[[type_CalypsoCard]]
==== Calypso Card

[cols="^.^1h,.^5", grid=rows, frame=all]
|===
| Name       | `CalypsoCard`
| Kind       | Interface
| Namespace  | `calypso.card.card`
| Extends    | `IsoSmartCard` (<<ref_cna_tr,CNA-TR-API>>)
| Since      | 1.0
| Purpose    | Dynamic view of the card's content, updated from selection to the end of the transaction.
|===

An instance of `CalypsoCard` is obtained by casting the `IsoSmartCard` object produced by the selection process
defined in <<ref_cna_tr,CNA-TR-API>>.

A `CalypsoCard` carries: application identification (revision, class, DF name, serial number, ATR, issuer), the indication of optional features (Stored Value, PIN, Rev 3.2 mode, ratification management), the management information of the modification buffer, the invalidation status and the files / counters / SV data read or modified during the transaction.

The `CalypsoCard` instance bound to a transaction is a *dynamic view* of the card image, updated after every successful command.
Failed write commands do not update the in-memory image.

[[op_CalypsoCardSelectionExtension_preparePreOpenSecureSession]]
===== Prepare Pre Open Secure Session

[cols="^.^1h,.^5", grid=rows, frame=all]
|===
| Signature
| `preparePreOpenSecureSession(` +
`{nbsp}{nbsp}{nbsp}{nbsp}writeAccessLevel: WriteAccessLevel` +
`) -> Self`
| Since          | 1.7
| Description
a| Adds a specific *Open Secure Session* command attempting a *pre-opening*. Enables a future single-exchange
session execution by anticipating the APDU responses.

The objective of the pre-opening is to allow the grouping of all the commands of a secure session. It is only
relevant for a distributed system where the ticketing processing is done remotely, so that a complete secure
session can be carried out in a single exchange between the server and the terminal.

To achieve that single exchange, all the data that will have to be read in session MUST first be read locally,
outside the session -- otherwise additional exchanges take place. The remote ticketing processing then prepares
all the commands of the session, from opening to closing, before executing it: `prepareOpenSecureSession(...)`,
then the other `prepare*` calls, then `prepareCloseSecureSession()`, and finally a single `processCommands()`.

The mechanism is *ineffective* if:

* the card or crypto module does not support extended mode;
* the session needs intermediate exchanges (PIN, SV, encryption, early mutual authentication, unread session
  data);
* the session opens with a different access level;
* an intermediate `processCommands()` is called;
* asymmetric cryptography is used.
| Parameters     | `writeAccessLevel` (<<type_WriteAccessLevel,`WriteAccessLevel`>>) -- the write access level of the session to pre-open.
| Returns        | The current instance (`Self`).
| Pre-conditions | *Argument* -- every parameter is non-`null`. +
  *State* -- no pre-open is already prepared.
| Errors         | None.
|===

[[op_SymmetricCryptoSecuritySettings_enableRatificationMechanism]]
===== Enable Ratification Mechanism

[cols="^.^1h,.^5", grid=rows, frame=all]
|===
| Signature      | `enableRatificationMechanism() -> Self`
| Since          | 2.0
| Description
a| Enables the ratification mechanism, which handles an early card removal preventing the terminal from receiving
the acknowledgement of the *Close Secure Session* command. Default: disabled.

When enabled, a ratification command is added after the closing command in contactless mode. The card considers the
secure session *ratified* only once it has processed that command: if the card is removed beforehand, the session
stays unratified in the card, which thus keeps the proof that the terminal may not have been informed of the
outcome. On cards where ratification happens on deselect, no ratification command is required (see
<<op_CalypsoCard_isRatificationOnDeselectSupported,`CalypsoCard.isRatificationOnDeselectSupported`>>).

* *Enable it* when the resumption MAY be handled by *another* terminal, since the proof of the interruption is then
carried by the card itself. Typical case: several gates on the same access line of a network.
* *Leave it disabled* when the resumption is necessarily handled by the *same* terminal, which keeps the context of
the interrupted transaction. Typical case: a remote ticket reloading server.

The mechanism can only be used within the anti-passback delay defined by the transport operator: beyond this delay,
an unratified session can no longer be handled as the resumption of an interrupted transaction.
| Returns        | The current instance (`Self`).
| Pre-conditions | None.
| Errors         | None.
| See also       | <<op_SecureTransactionManager_prepareCloseSecureSession,`SecureTransactionManager.prepareCloseSecureSession`>>, <<op_CalypsoCard_isRatificationOnDeselectSupported,`CalypsoCard.isRatificationOnDeselectSupported`>>

[[type_TransactionManager]]
==== Transaction Manager

[cols="^.^1h,.^5", grid=rows, frame=all]
|===
| Name       | `TransactionManager`
| Kind       | Interface
| Namespace  | `calypso.card.transaction`
| Extends    | `IsoCardTransactionManager` (<<ref_cna_tr,CNA-TR-API>>)
| Since      | 2.0
| Purpose    | Common operations for every Calypso card transaction. Prepare/process model. Extending `IsoCardTransactionManager` grants access to the multi-channel cast `asMultichannelCardTransactionManager()` defined by <<ref_cna_tr,CNA-TR-API>> when the underlying ISO/IEC 7816-4 card supports multi-channel.
|===

`TransactionManager` defines the full *prepare* command surface (file selection, reads, writes, counters, PIN, asymmetric key-pair generation).
The preparation step makes it possible to group commands together in order to minimise network data exchanges,
which is especially useful in a distributed architecture.
The bound `CalypsoCard` is updated after each successful APDU exchange, and parameter ranges are validated as documented in <<type_CalypsoCardSelectionExtension>>.

Processing of prepared commands is inherited from `CardTransactionManager` (<<ref_cna_tr,CNA-TR-API>>) via the
`IsoCardTransactionManager` supertype.
The Calypso `TransactionManager` does *not* redefine `processCommands()`; it relies on the inherited contract.
Multi-channel operations (`processCommandsAndCloseChannel`, `closeChannel`) are reached on demand through `asMultichannelCardTransactionManager()` of <<ref_cna_tr,CNA-TR-API>> when the underlying card supports multi-channel.

NOTE: Every write operation MAY raise <<type_SessionBufferOverflow,`SessionBufferOverflow`>> if the command would overflow the modification buffer and the multiple-session mode is not allowed.

[[op_HceTimeProvider_getCurrentLocalEpochSeconds]]
===== Get Current Local Epoch Seconds

[cols="^.^1h,.^5", grid=rows, frame=all]
|===
| Signature      | `getCurrentLocalEpochSeconds() -> Long`
| Since          | 3.0
| Description
a| Returns the current time expressed in the same time reference as the *SN Header* of a Calypso HCE application,
that is **local** time, as the number of seconds elapsed since 1 January 1970 at 0:00 in that same local reference.
The implementer provides the time reference it trusts, which MUST be the one in which the tokens of the targeted
applications were provisioned; the conversions and the comparison with the Calypso encoding are performed by the
card extension.

*Example.* At 11:30 local time on 1 January 2010, in a zone offset by one hour from UTC, for an application whose
SN Header is equal to `1`:

* from 1 January 1970 to 1 January 2010 there are 14610 days, so that day starts at
  `14 610 × 86 400 = 1 262 304 000`;
* 11:30 adds `41 400` seconds, so this operation returns `1 262 345 400`;
* the SN Header adds `1 × 43 200 = 43 200` seconds to the start of the same day, so
  <<op_CalypsoCard_getHceTokenExpiryLocalEpochSeconds,`CalypsoCard.getHceTokenExpiryLocalEpochSeconds`>>
  returns `1 262 347 200`, that is noon local time;
* `1 262 345 400` precedes `1 262 347 200`: the token is still valid, for thirty more minutes.

The offset from UTC never appears in the computation, both values being read from the same wall clock. Returning
the instant counted in UTC would give `1 262 341 800`, one hour less, and the key would appear valid for one hour too
long.
| Returns        | A strictly positive `Long`.
| Pre-conditions | None.
| Errors         | None.
|===

[[annex_external_requirements]]
== Conformance to external requirements

[NOTE]
This annex is _informative_. <<sec_conformance,Conformance>> defines what conforming *to this specification* means;
this annex states, requirement by requirement, how this specification stands with respect to an *external*
requirements profile, and records the reasons when a requirement is met through another mechanism, is deliberately
not exposed, or is left to the implementation layer.

Each requirement reviewed is given one of the following statuses:

[cols="^.^1,.^3", options="header"]
|===
| Status | Meaning

| Satisfied as stated
| The specification provides what the requirement asks for, in the form the requirement describes.

| Satisfied by an equivalent mechanism
| The intent of the requirement is met, through a mechanism that differs from the one it describes.

| Deliberately not exposed
| The capability is not offered to the upper layer, as a design decision stated in the corresponding note.

| Delegated to the implementation layer
| The capability belongs to the implementation or to its configuration, outside the surface of this API.
|===

[[annex_applicability_contexts]]
=== Applicability contexts

A requirement of the <<ref_cl_requirements,Calypso Layer requirements>> may carry one or more *applicability
contexts*. A context does not qualify the requirement but the layer itself: it states the kind of layer the
requirement applies to, and a requirement that carries several contexts applies only to a layer satisfying all of
them. This subsection states, for each context met by the requirements reviewed, under which conditions this
specification constitutes such a layer. The entries that follow then give, requirement by requirement, the
contexts it carries and the way this specification answers it.

No requirement group has been reviewed in this edition, so no context is listed yet.
